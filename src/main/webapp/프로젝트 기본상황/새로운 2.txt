현재 프로젝트는 전자정부프레임워크 3.8(Spring MVC + JSP + MyBatis) 기반이며, 예제 스타일을 많이 따라가고 있음.
Service/Controller/Util/DAO 전반에 `throws Exception`이 선언되어 있는 구조이며, 이는 전자정부 예제의 전형적인 스타일임.
현재는 스타일 통일을 위해 유지 중이며, 예외는 상위로 전파되는 흐름(DAO → Service → Controller → DispatcherServlet)을 이해한 상태임.

프로젝트의 권한 구조는 아래와 같음.

# 권한 구조

## USERS

* 사용자 테이블
* `role_no`로 권한그룹(USER_ROLE)을 참조
* `admin_yn`은 USERS가 아니라 USER_ROLE에 존재
* `use_yn` 존재 (현재는 사용자 활성 여부 의미)

## USER_ROLE (권한그룹)

컬럼 핵심:

* `role_no`
* `role_name`
* `admin_yn`
* `use_yn`
* `del_yn`

초기에는 `use_yn`을 논리삭제 용도로 사용했으나,
권한그룹 화면 요구사항에서:

* 사용 여부(use_yn)는 목록에 보여야 함
* 삭제 기능은 별도로 존재

하게 되면서 의미 충돌 발생.

그래서:

* `use_yn` = 운영 활성/비활성
* `del_yn` = 논리삭제

로 역할을 분리함.

현재 정책:

* 목록 조회 시 → `del_yn='N'`
* 실제 권한 사용 시 → `use_yn='Y'`

## MENU_PERMISSION (메뉴별 권한)

권한 컬럼:

* `disp_yn` : 사이드바 메뉴 표시 여부
* `view_yn` : URL 직접 접근 가능 여부
* `ins_yn`
* `upd_yn`
* `del_yn`

현재 구조는:

* USER → ROLE → MENU_PERMISSION
  형태의 전형적인 RBAC(Role Based Access Control) 구조임.

사용자별 권한 복사 구조가 아니므로:

* ROLE 수정 시 사용자 전체 권한이 자동 반영되는 구조임.
* 별도 USERS 업데이트는 필요 없음.

# 현재 권한 정책

## 1. 로그인 사용자 공통 접근 메뉴

권한체크 없이 로그인만 하면 접근 가능:

* 게시판
* 설문참여

## 2. 관리자 전용 메뉴

`ADMIN_YN='Y'` 인 Role만 접근 가능:

* 설문관리
* 권한관리

## 3. 일반 Role 기반 권한 메뉴

관리자가 아닌 경우:

* MENU_PERMISSION 기반 CRUD 권한 체크 필요

예:

* DISP_YN → 메뉴 표시
* VIEW_YN → URL 접근
* INS/UPD/DEL → CRUD 기능 제어

# 권한 처리 방향

인터셉터를 요청마다 여러 개 만드는 것이 아니라:

* 하나의 공통 AuthInterceptor에서 처리 예정

흐름:

1. 로그인 체크
2. 공개 URL 여부 확인
3. 관리자 URL 여부 확인 (`ADMIN_YN`)
4. 일반 Role 권한 체크 (`MENU_PERMISSION`)

현재 고려 중인 공개 URL:

* 게시판
* 설문참여

관리자 URL 예시:

* `/role/**`
* `/survey/manage/**`

일반 CRUD 권한은 URL 기반으로 판단 예정:
예:

* `/user/list.do` → VIEW_YN
* `/user/insert.do` → INS_YN
* `/user/update.do` → UPD_YN
* `/user/delete.do` → DEL_YN

menu_no는 URL 기준으로 MENU 테이블과 매핑하여 조회하는 방향을 고려 중임.

# 메뉴 처리 고민

현재는 각 Controller마다:

```java
MenuUtil.addMenu(model, menuService);
```

를 호출해서 사이드바 메뉴를 Model에 넣고 있음.

문제:

* 컨트롤러마다 반복
* 유지보수 불편

세션 저장도 고민했으나:

* 관리자가 메뉴 수정 시 즉시 반영 안 되는 문제 때문에 보류.

추천받은 방향:

* 메뉴는 layout/ajax 기반으로 별도 조회
* 권한 정보는 Session 저장 가능
* 메뉴 자체는 독립적으로 AJAX 렌더링 고려 가능

현재는 JSP + Map 바인딩 기반이며 DTO/VO 적극 사용 구조는 아님.

# 트랜잭션 이해 상태

이해한 내용:

* `@Transactional`은 `throws Exception` 자체가 중요한 것이 아니라,
  예외가 메서드 밖으로 전파되어야 rollback 됨.
* catch 후 예외를 삼키면 rollback 안 될 수 있음.
* Spring/MyBatis 예외는 대부분 `RuntimeException(DataAccessException)` 기반이라
  `throws Exception` 없이도 rollback 가능.
* 현재는 전자정부 스타일 유지 중이라 `throws Exception` 유지 예정.
